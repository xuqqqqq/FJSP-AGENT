# 可执行知识卡：FJSP with Machine Unavailability Windows (Non-Crossable, Non-Resumable)

## 1. 问题语义
- **核心问题**：柔性作业车间调度问题（FJSP）中，机器因预防性维护（PM）或其它原因存在**预先给定的不可用时间窗口**。  
- **不可用窗口**：每台机器上存在若干维护任务，每个任务有确定的持续时间以及在某个时间窗内必须被执行；维护期间机器不可用于加工 [[1](Section 2), [2](Section 2.1)]。  
- **操作不可中断且不可跨越**：操作不能中断，也不能与不可用窗口有任何重叠；若操作与维护时间冲突，则该操作必须重新整体执行（non‑resumable）[[1](Section 2)]。  
- **目标函数**：通常是最小化最大完工时间（makespan）、总机器负载、关键机器负载等[[1](Section 2)]。  
- **与标准 FJSP 的区别**：机器不再“持续可用”，而是附加了一组不可用时间段，调度时必须保证每道工序完全落在机器的可用时段内。

## 2. 半开区间规则 [start, end)
- **统一采用半开区间**：所有时间区间（操作、不可用窗口、机器占用）均表示为 `[start, end)`。  
  - 不可用窗口：`[maint_start, maint_end)`  
  - 操作区间：`[op_start, op_end)`  
- **重叠检测**：操作与不可用窗口冲突当且仅当 `op_start < maint_end AND op_end > maint_start`。  
- **边界处理**：操作可以在 `maint_end` 精确开始，不会冲突；同样操作可以在 `maint_start` 精确结束（若结束时间等于 maint_start），但操作本身不能跨入不可用窗口。  
- **原因**：避免闭区间在相邻区间上引起的“包含/排除”歧义，并简化区间合并与间隙计算。

## 3. Calendar‑Aware Decoder
- **机器日历**：为每台机器维护一个有序的不可用区间列表（按开始时间排序），并根据这些区间推导出**可用时段**（空闲区间）。  
- **解码逻辑**（基于最早开始时间）：  
  1. 遍历作业的操作序列，对每个操作根据机器选择结果确定目标机器。  
  2. 确定操作的**最早可用开始时间** = max(前道工序完成时间, 机器当前可用时间)。  
  3. 在机器日历中寻找满足 `duration` 的**第一个空闲段**，使得操作完全落在一个空闲段内且不与任何不可用区间重叠。  
  4. 若找到，设置操作开始时间；否则说明当前调度不可行（需修复或拒绝）。  
  5. 更新机器的占用状态（添加一个操作占用区间，但不改变不可用窗口）。  
- **关键点**：不可用窗口的持续时间已经计入机器的“阻塞”，解码器不需要修改维护任务的固定区间，只需保证操作不与其重叠。  
- **证据**：维护任务一旦调度就产生了一个不可用期间，在此期间“不允许处理任何操作”[[1](Section 2)]；且操作不可抢占[[2](Section 2.1)]，故 calendar 必须保证整个操作区间完全在可用部分。

## 4. Availability‑Aware Insertion
- **插入式启发式**（如贪心插入、构造启发式）：  
  - 对于待插入操作，遍历目标机器的所有空闲隙（由不可用窗口和已调度操作分隔出的区间）。  
  - 找到一个长度 ≥ 操作加工时间的空闲隙，且其开始时间不早于该操作的前序完成时间。  
  - 插入后可能需要**右移**该机器上后续操作以腾出足够连续空间，但仍需满足与不可用窗口不重叠的约束。  
  - 若插入造成不可行（例如右移后某操作跨入维护窗口），则此插入位置非法。  
- **可用性检查函数**：`can_insert(machine, start, duration)` → 检查区间 `[start, start+duration)` 是否与该机器的所有不可用窗口以及已固定操作无交叠。  
- **证据依据**：维护任务有确定的时间窗和持续时间，不可抢占意味着操作不能与维护任务的执行时段重叠[[2](Section 2.1)]，因此插入时必须验证整个时段。

## 5. 局部搜索 Move Delta
- **典型移动**：更改一个操作的机器分配（machine reassignment）或交换同机器上两个操作的顺序（swap）。  
- **Delta 评估步骤**：  
  1. 记录受移动影响的操作集合（通常为若干工序）。  
  2. 移除这些操作，使机器恢复空闲状态，但保留不可用窗口。  
  3. 按照新的顺序/机器重新插入这些操作（使用 calendar‑aware 插入），得到新的开始/结束时间。  
  4. 计算新 makespan 与旧 makespan 的差异。  
- **可行性快速检查**：若某个移动后的操作无法在允许的机器上找到合法时间窗（即所有空闲段不足以容纳持续时间或开始时间违反前序约束），则移动不可行，可直接丢弃。  
- **精细化**：移动评估时需考虑因不可用窗口导致的额外空闲时间对后续操作链的影响（右移链可能会被维护窗口放大 makespan）。  

## 6. Repair & Self‑Check
- **目的**：在解码后或邻域移动后，自动修复可能偶然违反维护约束的调度。  
- **修复策略**：  
  - 遍历每台机器上的操作序列，检查每个操作区间是否与不可用窗口重叠。  
  - 若重叠，将该操作及其后续操作整体**延迟**至冲突维护窗口之后，并递归调整后续机器的空闲状态。  
  - 如果延迟后导致 makespan 显著增加或与其他约束冲突，可考虑将操作重新分配到其它可选机器上。  
- **自我检查函数**：返回所有违反 `[maint_start, maint_end)` 约束的操作位置，用于调试和记录。  
- **依据**：不可用窗口是硬约束，必须被满足[[1](Section 2)]，因此任何调度方案都应具备合法性检查能力。

## 7. 常见错误
1. **忽略维护窗口的持续时间**：只判断开始时间是否在窗口外，但操作可能横跨整个窗口。  
2. **闭区间产生的边界 bug**：例如将维护窗口定义为 `[start, end]`，导致无法区分操作在 `end` 时刻开始是否合法。  
3. **未按机器独立管理日历**：每台机器的不可用窗口不同，错误共享机器日历会导致约束遗漏。  
4. **插入时只检查开始时刻**：未验证整个操作区间与所有不可用窗口的交叉情况。  
5. **解码器未考虑前序工序的完成时间**：可能导致操作比预期更早开始，但实际被维护窗口打断。  
6. **局部搜索评估直接使用原有时间戳**：移动后未重新调用 calendar‑aware 插入，错误的保留旧开始时间，导致 makespan 计算失真。  

## 8. 从标准 FJSP 到含不可用窗口约束的实现 Checklist
- [ ] **数据结构**：为每台机器创建 `unavailable_intervals` 列表，保存半开区间 `[maint_start, maint_end)`，按开始时间排序且无重叠。  
- [ ] **日历构建**：根据不可用区间和已调度的操作，动态推导机器的可用段（例如使用间隔树或简单线性扫描）。  
- [ ] **可行性检查函数**：`is_interval_available(machine, start, end)` → 检查 `[start, end)` 是否完全落在某个可用段内。  
- [ ] **最早开始时间查找**：`find_earliest_start(machine, duration, earliest_start)` → 返回≥earliest_start 且满足区间可用性的最早开始时间。  
- [ ] **解码器**：对每个操作用 `find_earliest_start` 安排，并更新机器占用（不修改不可用区间）。  
- [ ] **插入操作**：在构造启发式或局部搜索中，使用上述函数寻找插入点，并实现右移逻辑（右移时同样调用 `find_earliest_start`）。  
- [ ] **移动评估**：复制部分调度状态，执行移除-插入，比较 makespan 变化，遇到不可行则直接跳过。  
- [ ] **修复例程**：提供一个 `repair(schedule)`，检测并延迟冲突操作，或输出冲突列表。  
- [ ] **单元测试**：构造包含少量作业和机器的实例，其中某些机器的特定时间段完全不可用，验证 makespan 计算、是否产生冲突。  
- [ ] **性能标定**：与文献基准（如 FJSSP‑nfa 实例[[2](Section 3.1)]）对比，确保算法所得 makespan 不低于已知最优（或确保无无效解）。
