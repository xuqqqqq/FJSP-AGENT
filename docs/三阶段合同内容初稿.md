# 面向FJSP及其变种的算法自演进框架技术合作项目合同内容初稿

> 本文为合同条款讨论稿，基于原《复杂柔性作业车间调度算法技术合作项目》阶段结构，并结合后续关于 AlgoForge / Loop Engineering / FJSP 垂直增强框架的讨论整理。正式合同中的项目周期、验收指标百分比、测试集范围、付款节点和知识产权条款需由双方进一步确认。

## 一、项目名称

面向FJSP及其变种的算法自演进框架与铝加工调度求解技术合作项目。

## 二、项目目标

本项目围绕复杂柔性作业车间调度（Flexible Job Shop Scheduling Problem，FJSP）及其工业变种，开发一套可审计、可复现、可扩展的算法自演进框架。该框架能够读取用户提供的需求文档、输入输出接口文档、算例数据和评价器，在约定的迭代轮次或时间预算内，自动生成、评估、反思并修订调度求解算法，最终输出满足约束条件并具有较好求解质量的算法代码和实验报告。

项目总体思路为“通用算法自演进 Harness + FJSP 领域知识增强”：

1. 通用 Harness 层不绑定单一调度场景，负责文档摄入、任务契约生成、项目健康检查、基准评测、实验隔离、版本管理、日志审计、评价器调用、指标汇总和报告生成。
2. FJSP 领域增强层通过 Skill、知识库、算例适配器、评价器插件、算法策略卡和局部搜索算子库实现，用于提升 Agent 对 FJSP 及其变种问题的理解、代码生成和自我修正能力。
3. 铝加工调度场景作为重点工业验证场景，在已有基线算法和已沉淀的领域经验基础上，验证框架对复杂工业约束、完整合法解生成、指标优化和实验复盘的支撑能力。

## 四、技术路线

### 4.1 总体架构

系统采用“主控 Agent + Coding Agent + 可信 Harness / Evaluator”的闭环结构：

1. 主控 Agent 负责读取需求文档、输入输出文档和用户目标，生成任务契约、意图对齐摘要、实验计划、候选策略和任务记忆。
2. Coding Agent 负责在隔离工作区内生成或修改求解算法代码，并输出结构化的修改说明、策略说明和自评结果。
3. Judgment Agent 负责在关键节点判断生成的问题描述、策略说明和代码修改是否满足提示要求，是否存在明显语法错误、接口错误或逻辑风险。
4. Revision Agent 根据 Judgment Agent 或 Error Analysis Agent 的反馈，修订问题描述、策略说明或代码。
5. Error Analysis Agent 在代码运行失败、评价器失败或输出非法时进行错误归因，并生成下一轮可执行的修复建议。
6. Harness / Evaluator 由系统或人工确认后固定，负责最终合法性验证、指标计算、候选解比较、实验记录和结果归档。LLM 或 Coding Agent 不得自行篡改评价器或将自评结果作为最终验收依据。

### 4.2 自演进闭环

每个自动演进任务至少包含以下流程：

1. 文档摄入：读取需求文档、输入输出文档、算例说明、评价指标说明。
2. 任务契约生成：抽取硬约束、软约束、优化目标、输入输出格式、运行预算和验收口径。
3. 意图对齐：生成可审查的任务摘要，确认目标、基线、评价器、测试集和允许修改范围。
4. 基线评测：运行初始算法、常见派工规则或用户指定算法，得到 baseline 指标。
5. 策略生成：基于文档、知识库、历史实验和当前失败原因，提出候选算法策略或代码修改方向。
6. 代码生成 / 修改：Coding Agent 在隔离工作区内生成或修改求解器代码。
7. 预执行判断：Judgment Agent 检查代码结构、接口、语法、禁止修改范围和明显逻辑风险。
8. 运行评价：Harness 调用固定求解命令、validator 和 benchmark，记录合法性、目标指标和运行时间。
9. 错误分析与反思：对非法解、运行错误、无提升结果和过拟合风险进行结构化总结。
10. 假设图更新：保留有效策略，修剪无效策略，避免重复尝试同质化方案。
11. 版本归档：对有效候选版本进行 Git 记录，保留实验日志和可复现命令。
12. 报告生成：输出最终代码、最佳版本、实验复盘、指标曲线、失败策略和后续建议。

### 4.3 FJSP 领域增强

FJSP 领域能力通过以下方式实现：

1. 建立 FJSP 及其变种问题的本地知识库，内容包括论文方法卡、经典派工规则、元启发式算法模板、局部搜索邻域、禁忌搜索禁忌属性、快速评估方法和典型约束处理策略。
2. 建立标准 FJSP 算例适配器，支持常见公开测试集格式读取、best-known 指标对比和 gap 计算。
3. 建立工业 FJSP 变种适配器，支持释放时间、维修窗口、顺序相关 setup、最大 / 最小生产间隔、替代路径、转运时间、优先级和组批等约束的输入输出转换。
4. 建立领域 Skill 或插件，使主控 Agent 能在生成策略前主动检索相关约束处理方式、邻域动作和已知失败经验。
5. 支持策略级演进与代码级演进两类路径：策略级演进调整派工规则、评分函数、参数和算子选择；代码级演进可在允许范围内新增或修改求解器模块、局部搜索算子、修复算子和路径选择逻辑。

## 六、建议验收指标口径

为避免“xx%”指标在后续验收中产生争议，建议合同中将指标分为基础验收指标、提升验收指标和挑战指标。

### 6.1 基础验收指标

1. 可运行性：系统能够在本地环境中完成任务创建、文档摄入、健康检查、基线评测、迭代执行和报告生成。
2. 可审计性：每轮实验必须记录输入、策略、代码修改、运行命令、指标、错误和版本。
3. 合法性：任何最终候选结果必须通过固定 evaluator / validator；非法结果不得进入最佳候选。
4. 可复现性：封存测试集、配置文件、随机种子、代码版本和运行命令应能复现实验结果。
5. 功能覆盖：FJSP 必选特性和扩展特性应在测试报告中给出覆盖算例、验证方法和结果。

### 6.2 提升验收指标

具体百分比建议在第一阶段基线评测完成后填入。推荐采用如下口径：

1. 相较常见派工规则基线：在相同求解时间预算下，平均求解质量提升不低于【待定】%。
2. 相较经典启发式 / 元启发式基线：在相同求解时间预算下，平均求解质量提升不低于【待定】%，或在求解质量相近时运行时间降低不低于【待定】%。
3. 相较直接 LLM 生成算法：在相同提示材料、相同迭代轮次或时间预算下，可行满足率提升不低于【待定】%，平均求解质量提升不低于【待定】%。
4. 相较无知识库 / 无 Skill 版本：在相同测试集和预算下，有知识库版本的可行满足率、平均求解质量或有效迭代率至少一项提升不低于【待定】%。
5. 相较开源 LLM 优化框架：在能够复现实验的前提下，与 LLM4OPT、HeurAgenix 等开源框架在同一测试集、同一评价器和同一预算下进行对比，提升指标由双方根据可复现结果确认。

### 6.3 铝加工测试集指标

铝加工测试集建议不直接与标准 FJSP benchmark 的指标混用，应单独封存：

1. 算例版本、输入文件 hash、评价器版本和校验器版本。
2. 时间口径，例如 current_time、horizon、维修窗口闭开区间、是否允许提前 1 分钟启动等。
3. 组批口径，例如有限组批、无限组批、同 family 组批、批次容量和批次时长计算方式。
4. 目标优先级，例如产量优先、setup 次数次优、交期达成率或完整任务数约束。
5. 当前基线结果和当前最优结果。

建议主验收指标设置为：在封存口径下输出完整合法解，且相较双方确认的当前基线至少一项核心指标提升。更高产量、更低 setup、更高交期达成率等目标可作为挑战指标或 Bonus 指标。

## 七、Bonus 与挑战成果

以下成果建议作为 Bonus 或挑战条款，不作为基础验收失败条件：

1. 产出与算法自演进框架、FJSP 领域增强、评价器驱动闭环、错误诊断或知识库增强相关的专利交底书或专利申请。
2. 自演进框架相较直接大模型生成算法，在可行满足率、平均求解质量、有效迭代率或错误修复成功率方面取得显著提升。
3. 在铝加工测试集上达到此前约定的较高优化目标之一，例如更高产量、更低切换次数、更高交期达成率或更高运行效率。
4. 实现大规模问题分解挑战特性，并在求解质量不变差的情况下提升求解效率。
5. 支持更多 Coding Agent 后端、Docker 隔离、多 worker 并行、隐藏测试集评估或跨问题迁移。

## 八、双方职责建议

### 8.1 甲方职责

1. 提供或确认需求文档、输入输出文档、测试算例、评价指标和验收口径。
2. 提供或确认正式 evaluator / validator。若 evaluator / validator 由乙方生成，需经甲方确认后方可作为正式验收依据。
3. 提供当前基线算法或基线结果，用于计算提升幅度。
4. 协助确认公开测试集、构造变种测试集和工业测试集的使用范围。
5. 对阶段交付件进行评审，并在必要时给出修改意见。

### 8.2 乙方职责

1. 设计并实现算法自演进 Harness、FJSP 领域增强模块和相关工具链。
2. 维护实验记录、代码版本、测试报告和交付文档。
3. 在约定测试集和评价器下完成基线评测、消融实验和最终对比实验。
4. 对 LLM / Coding Agent 生成的代码进行隔离运行、合法性验证和审计记录。
5. 对无法达到的挑战指标给出实验依据、失败原因和后续改进建议。

## 九、风险与边界

1. 本项目不承诺在所有 FJSP 公开算例上超过领域 SOTA 算法，验收基线应限定为双方约定的常见派工规则、经典启发式算法、直接 LLM 生成算法或可复现开源框架。
2. 若测试集规模过小或仅有单一工业算例，框架可在当前算例上优化，但最终报告应明确过拟合风险。
3. 若评价器、validator 或测试数据在阶段验收过程中发生变更，应重新封存版本并重新计算 baseline。
4. 若外部 LLM API、Coding Agent 工具或模型服务不可用，应允许切换到双方确认的替代后端；替代后端的结果需重新记录。
5. LLM 生成的解释、策略或自评不作为验收依据，所有验收以固定 evaluator / validator 和双方确认的测试报告为准。
6. 代码级自演进存在生成错误、无效修改和引入新依赖的风险，系统应通过工作区隔离、禁止修改范围、预执行判断和固定评价器降低风险。

## 十、建议写入合同的关键表述

为降低后续争议，建议在正式合同中明确写入以下表述：

1. “算法自演进框架的核心验收对象为框架能力、可审计闭环、FJSP 领域适配能力及在约定测试集上的实测提升，不以超过所有公开 SOTA 算法作为验收条件。”
2. “正式验收结果以双方确认的 evaluator / validator、测试集版本、运行预算和评价指标为准。LLM 自评结果、自然语言解释或未通过 validator 的结果不得作为验收依据。”
3. “自演进 10 轮 / 30 分钟中的 30 分钟指主控 Agent 进行文档理解、策略生成、代码生成、反思修订和调度的时间，不含固定 evaluator / benchmark 的算法评估时间；候选算法求解时间预算另行约定，并对所有对比算法保持一致。”
4. “FJSP 领域能力通过知识库、Skill、插件、适配器和评价器实现；通用 Harness 层不因某一工业场景而写死业务规则。”
5. “铝加工测试集作为重点工业验证场景，其指标以双方封存算例、评价口径和当前基线为准；若达到更高挑战指标，可作为 Bonus 或挑战成果。”
