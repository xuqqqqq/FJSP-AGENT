# 并行组批 FJSP 适配

## 语义不变量

1. 严格解析 Fattahi 主体后的批机容量和逐工件 family 尾部，不得忽略剩余 token。
2. 普通机器的活动是一道工序；批处理机的活动是一个批次。机器互斥必须比较批次区间，不能把同批成员误判为重叠。
3. 同批成员必须在同一机器、属于同一 family、数量不超过容量，并共享相同开始和结束时刻。
4. 批次时长必须等于成员所选加工时长的最大值。成员自己的 schedule 区间写整个批次时长。
5. 工件前置从前序所在批次的结束传播到后序；family 只表示组批相容性，不产生优先关系。

## 方法适配

- 构造搜索：维护工序就绪集合，先选机器，再在同族就绪工序中形成不超容量的批；比较立即开批与有限等待合批，不允许为等候未来成员而无限阻塞。
- 耦合局部搜索：至少支持同族批合并、批拆分、成员移批、整批重插和批机/普通机换机。每次移动后完整重算批时长、工件就绪和机器批序。
- 群体/模因：染色体编码机器选择、批归属和批序；交叉变异后只能通过统一批解码器恢复合法性，不能缓存旧开始时间。
- 精确混合：为每台批机建立有界批槽。用成员选择变量、family one-hot、容量约束和 `AddMaxEquality` 表达批时长；一个可选批区间参加机器 `NoOverlap`，成员语义起止与所选批区间相等。普通候选仍用单工序可选区间。
  presence 条件只能通过 `only_enforce_if` / `OnlyEnforceIf` 施加，禁止使用不存在的
  `only_if` / `OnlyIf`。必须先运行一个包含实际条件约束的最小建模 probe，再运行完整模型。
  普通机器候选与批槽成员都不得让未选择候选约束共享语义起止；候选加工时长等式必须受对应
  presence 控制。至少用一道具有不同候选时长的工序验证模型不会被误建成 `INFEASIBLE`。
  批槽 presence 必须等价于成员布尔变量的 OR：`presence >= member_i` 且
  `presence <= sum(members)`。容量大于 1 时禁止 `presence == sum(members)`，因为 presence 是
  BoolVar，该等式会把每个槽强制成最多一个成员，悄悄禁用并行组批。
  horizon 使用合法 incumbent makespan 或全体工序候选最大时长总和等安全上界，不能使用最长
  单个 job 的加工时长和。
  对专门验证并行组批能力的小算例，完整 exact 模型必须要求至少一个批槽含两个或更多同族成员，
  并在该约束下最小化 makespan；不能用全单件批的无约束 makespan 最优解代替组批能力验证。
  可为每个槽建立“多成员”布尔量并约束至少一个为真，或使用等价线性约束。最终是否真实合批
  只认固定 Core evaluator 重算的 `best_metrics.grouped_batch_count > 0`，不能使用 solver 按非空批槽
  数量自报的计数。
  在这种能力验收任务中，最终候选选择必须先过滤为合法且真实含多成员批的排程，再在这些排程
  之间最小化 makespan。不能仅因强制合批解的 makespan 不优于退化单件批 incumbent 就拒绝它并
  输出后者；否则 exact 虽运行，最终 Core 激活证据仍必然为 0。

## 验收证据

- 报告批机数、实际批次数、合批数以及容量、family、同步和批时长违反数。
- 搜索 lane 必须报告实际执行的合并/拆分/移批或批槽求解计数。
- 只有真实调用精确求解器并成功提取完整合法排程，才能声明 exact 已运行。
- 对明确用于验证组批能力、且存在同族兼容工序与容量余量的小算例，`grouped_batch_count=0`
  只能证明退化单件批可行，不能证明 PBPM 搜索机制已跑通。能力验收必须产生至少一个由固定
  evaluator 验证的合法真实多成员批；“无约束最优解没有合批”不能替代该能力证据。
