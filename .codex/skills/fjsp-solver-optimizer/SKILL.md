# FJSP 求解器优化

把本 Skill 作为领域方法库，不要把它当成固定流水线。根据项目实现、冻结评测口径、当前证据和剩余研究范围，自主选择值得验证的方向。算法实现属于 Skill、知识库、Method Package 和 Coding Worker；通用后端只负责任务编排、证据和门禁。

## 让 Skill 真正进入实现

读取本文件或在回复中提到 Skill 名称不算产生效果。一次有效使用至少应建立下面的因果链，但表达形式由 Agent 自主决定：

- 从解析器、实例和当前解取得结构证据，判断主要压力来自机器分配、机器内顺序、解码器、搜索多样性还是时间分配。
- 提出一个可证伪假设，并指出本 Skill 中哪条方法为什么适合当前结构；不要把多起点、局部搜索、CP-SAT 等名词无差别叠加。
- 把方法映射到当前仓库中的具体函数、数据结构或搜索阶段，留下真实代码差异。
- 使用与 Baseline 语义一致的局部命令比较改动前后结果；同时检查正确性、耗时和解的结构变化。
- 无可信收益时回退无效差异并保留失败结论；有收益时把差异留在当前候选工作区，向主 Agent 返回精确 assignment ID、改动文件、命令、指标和风险。

第一轮不要只看最终 makespan。先比较现有求解器在 assignment 与 sequence 两个维度实际产生了多少不同结构、最优改进发生在哪个阶段、预算主要花在哪里。后续轮次先读假设图、已验证经验和正式 evaluator 证据，确认新假设不是对旧路线换一种措辞。Skill 提供研究压力和方法，不替代项目代码、局部实验或正式评测。

## 先对齐 Harness 事实

- Main Agent 先读取不含具体 Method Package 的有界选择包，根据需求、IO、实例诊断和历史证据选择方法族；Harness 定向检索后，Main 再读取实现卡与匹配包，形成完整方向和任务书。
- Coding Worker 只读取 Main 下发的 `WorkerAssignment`、当前候选代码和被选中的少量知识资产；不得看到完整 Context Packet，也不得自行换方向或换方法包。
- Worker 可以编译并运行一次固定种子的短 smoke。这些结果只用于诊断，不能替代正式 evaluator。
- Agentic Judgment 检查越权、后端依赖、声明与实现一致性；Semantic Reviewer 检查算法语义和完整覆盖；二者的具体阻断项进入同方向最小修补。
- Core evaluator 独立判断合法性和 makespan。只有严格优于 incumbent 且所有硬门禁通过的候选才能 promotion，否则 rollback。
- 运行产生的候选经验留在输出目录的分层记忆中；未经 promotion 和语义证据确认，不得写成稳定方法知识。

## 诊断问题结构

先从代码、实例和已有解中计算或估计：

- 每道工序的可选机器数量分布，以及具有多个选择的工序比例。
- 同一工序不同机器加工时间的跨度。
- 工序数、作业数、机器数和机器负载上界。
- 当前解的关键路径、关键机器块、最长关键块和近关键工序。
- 关键路径附近仍可换机的工序数量。
- 搜索池的 assignment/order 指纹是否实际上收敛到同一结构。

只能按结构特征选择策略。不要按实例文件名、Benchmark 家族、已知最优值、保存的最佳解或挑选过的随机种子路由。

## 选择主要研究压力

| 结构 | 主要困难 | 优先研究 |
| --- | --- | --- |
| 低柔性、加工时间无跨度 | 机器顺序容易坍缩到同一盆地 | 多样化构造、关键块交换/插入、窗口重排 |
| 低柔性、存在加工时间跨度 | 分配和顺序相互耦合 | 小型 assignment trust region、关键块邻域、短响应探测 |
| 中等柔性 | 选择真正有用的分配多样性 | 特征驱动构造、有限前瞻、分配感知邻域 |
| 高柔性且缺少稳定关键结构 | 分配空间巨大，浅层换机扫描覆盖率很低 | 空闲间隙感知关键压力构造、状态去重 Beam、多规则组合；再按证据追加局部精修 |

高柔性不是“禁止局部搜索”的标签。若 incumbent 显示瓶颈稳定集中在少数关键工序/关键块，
或候选实现具备完整迭代式 VND/Tabu 闭环，局部搜索仍可能合适。若只有一次、几十个 move 的
浅扫描，应先比较构造式 Beam 的覆盖状态数、合法 makespan 和耗时。详细蓝图由 Domain Pack
标签 `constructive_search`、`beam_search`、`idle_gap`、`critical_dispatch` 定向检索。

阈值必须从当前项目和实例分布推断。不要把平均可选机器数等经验阈值写成跨项目常量。

## 形成可验证的研究回路

1. 基于结构和历史证据提出一个可证伪假设，例如“关键机器块顺序而非分配限制了当前 Best”。
2. Main Agent 把一个方向编译成有界 `WorkerAssignment`，明确目标、完整交付物、实现顺序、保留项、禁改项和检查预算。
3. Coding Worker 在候选工作区完成实现和一次短 smoke，保持可行 incumbent，记录改动与风险；没有可信结果时如实返回。
4. JA 或 Semantic Reviewer 给出具体阻断项时，Main 保持方向、方法包和 lineage 不变，只下发覆盖这些阻断项的最小修补。
5. 通过静态门禁的候选交给 Core evaluator，以独立合法性和 makespan 作为正式事实。
6. 只有严格改进且语义完整的候选进入 incumbent；合法但不提升、变差或阻断未修复的候选 rollback。
7. 每轮结束更新假设图和分层经验；只有经 promotion 验证的机制可作为后续轮次的保护事实。

避免重复提交语义相同的路线。先看假设图和失败记录；同一候选需要复跑时说明随机性、外部条件或独立复核原因。

## 设计分层求解器

候选方向通常可以从以下层次组合，不要求每个项目全部具备：

1. 构造少量真正不同的可行解。
2. 只改进小型精英且结构多样的集合。
3. 围绕关键结构生成有界的顺序与分配邻域。
4. 用短求解探测入口是否可修复，而不是直接消耗全部预算。
5. 选择两三个互补入口，把最大连续预算留给主要最终改进。
6. 任一阶段失败、超时或退化时返回当前最佳可行解。

把构造、探索、探测和最终改进分开计时和记录，才能判断停滞来自弱初解、伪多样性、错误选择器还是最终预算不足。

具体策略见 [references/optimization-playbook.md](references/optimization-playbook.md)。实现解码、关键邻域、trust region 或入口选择时见 [references/core-pseudocode.md](references/core-pseudocode.md)。修改成熟求解器或解释证据前见 [references/lessons-and-pitfalls.md](references/lessons-and-pitfalls.md)。

## 守住泛化与证据边界

- 不搜索或保存“效果最好”的随机种子。
- 不把 Baseline、已知下界、已知最优值或历史最佳解偷偷放入搜索决策。
- 不增加实例名分支、单实例常量或对 evaluator/trustedFiles 的修改。
- 下界只用于通用质量信号、停止条件或证明，不作为答案泄露。
- 多线程 CP-SAT 即使关闭随机搜索也可能有噪声；用稳定协议解释结果。
- 新策略先保持可替换和可回退，只有跨结构相近实例的正式证据支持时才扩大适用范围。
- 不把一次幸运运行、局部 Benchmark 或“探测增益很大”包装成 Best 改进。
